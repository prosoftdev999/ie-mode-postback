# IE Mode Postback

A legacy-browser reconstruction project focused on recovering the exact form values posted by a retired Windows line-of-business application that embedded Internet Explorer.

The application was used by a customs brokerage to lodge import, export, and amendment entries. Its gateway no longer has copies of the original POST bodies, but the client screens and a journal of the values keyed by clerks remain.

The objective is to reproduce what the embedded Internet Explorer control actually placed into each named form control immediately before submission.

## Overview

The archived client displayed several HTML entry screens inside a .NET Windows Forms `WebBrowser` control.

When a clerk clicked **Lodge entry**, JavaScript on the page:

```text
keyed controls
      ↓
legacy JavaScript processing
      ↓
hidden-field updates
      ↓
DOM value changes
      ↓
form submission
```

The reconstruction must reproduce the state at the bottom of that pipeline.

This is not simply a matter of copying values from the journal. The scripts transform those values, and their behavior depends on the Internet Explorer document mode in which each screen ran.

## Document Modes

The three screens do not execute under identical Internet Explorer behavior.

Their effective document modes must be reconstructed from the HTML and the behavior of the embedded browser control.

Examples include:

- IE7-compatible behavior
- IE8 document mode
- IE11 / edge mode

A compatibility declaration does not automatically take effect if it appears too late in the document.

For example, an `X-UA-Compatible` declaration that follows script execution can behave differently from one declared early enough to control the document mode.

This matters because the same JavaScript can produce different results under different IE modes.

## Legacy JScript Behavior

The older document modes expose Microsoft JScript semantics that differ from modern JavaScript engines.

Relevant differences include behavior around:

- `parseInt`
- regular-expression whitespace
- `split`
- `substr`
- string indexing
- `getYear`
- `toFixed`
- `toDateString`
- `toLocaleDateString`
- `toLocaleString`
- `JSON`
- date parsing and overflow

A modern Node.js execution of the archived scripts therefore does not reproduce the historical browser output exactly.

## DOM Compatibility

Internet Explorer's DOM behavior is also part of the reconstruction.

In legacy document mode, `getElementById` can behave differently from modern standards-oriented implementations.

In particular, older IE behavior can match elements by their `name` as well as their `id`.

That distinction can change which element a script reads or writes.

Conceptually:

```html
<a name="txtWeight"></a>
<input id="txtWeight" name="weight">
```

A legacy lookup can resolve differently from a modern browser lookup.

This affects downstream form values.

## Form-State Reconstruction

For every journal entry, the solver reconstructs the corresponding screen and applies the historical browser semantics.

Conceptually:

```text
journal entry
      +
screen HTML
      +
screen JavaScript
      +
document mode
      +
legacy engine semantics
      ↓
final form-control values
```

The result must include every:

```text
input
select
textarea
```

inside the form that has a `name` attribute.

No additional controls are included.

## Hidden Fields

Several values are generated by scripts rather than directly entered by the clerk.

Examples can include:

- references
- sequence identifiers
- normalized party information
- formatted addresses
- dates
- docket descriptions
- calculated values
- serialized invoice data

These fields must reflect the value present after page scripts have executed.

## Date Semantics

Date handling is one of the major compatibility areas.

The archived client can encounter:

- US-style dates
- European-style dates
- UK-style dates
- ISO dates
- two-digit years
- month-name inputs
- overflowing month/day values
- local versus UTC interpretation

Different document modes and JavaScript engines can interpret these forms differently.

A value that modern JavaScript treats as invalid may have been accepted or normalized by the historical client.

## Windows Locale Formatting

The archived client ran in a Windows environment.

Therefore, locale-sensitive operations must reflect the historical Windows behavior rather than whatever formatting a current Linux or modern JavaScript runtime happens to use.

Examples include:

```text
toLocaleDateString()
toLocaleString()
```

The task's captured environment used an English-US locale and Eastern time.

## Newline Handling

Textarea values require special attention.

In older Internet Explorer modes, text written into a textarea can normalize line endings differently from modern engines.

For example:

```text
LF
```

can become:

```text
CRLF
```

in the DOM value exposed by the legacy screen.

The output requires the actual control value rather than an HTTP-encoded representation.

Line breaks therefore matter character-for-character.

## Unicode and Whitespace

The journal intentionally includes realistic pasted business data.

Examples include:

- non-breaking spaces
- wide spaces
- soft hyphens
- zero-width characters
- directional characters
- German sharp s
- accented names
- international addresses

Legacy JavaScript does not always treat those characters the same way as modern ECMAScript engines.

Whitespace tests and case conversion therefore need to reflect the appropriate historical mode.

## JSON Compatibility

The oldest screen can depend on a JSON compatibility script rather than the browser's native JSON implementation.

That can affect which characters are escaped when structured data is serialized.

Consequently:

```text
JSON.stringify(...)
```

under a modern engine is not always a valid substitute for the historical behavior.

## Exact Value Semantics

The required artifact represents DOM control values immediately before submission.

It does **not** represent URL-encoded or multipart HTTP form serialization.

If a control's value is:

```text
LINE 1
LINE 2
```

the JSON output must contain the actual line break representation held by the DOM.

Values are compared character-for-character.

## Output

The solver writes:

```text
/app/output/postback.json
```

with the structure:

```json
{
  "entries": {
    "E10001": {
      "field_name": "value"
    }
  }
}
```

`entries` must contain exactly the entry IDs present in the journal.

Each entry contains every named:

```text
input
select
textarea
```

from that screen's form and nothing else.

Empty controls are represented as:

```json
""
```

A simplified example is:

```json
{
  "entries": {
    "E10001": {
      "ref": "AM-14-000001",
      "ref_seq": "000001",
      "party": "ACME LTD",
      "addr1": "1 MAIN ST",
      "docket": "AM AM-14-000001 / Mon Jan 13 2014 / 1 line(s)"
    }
  }
}
```

The example only illustrates the structure. The actual entries contain all named form controls required by the archived screens.

## Scale

The project contains a substantial set of historical entry records spanning:

- import entries
- export entries
- amendment entries

The task metadata describes 1,644 retained entries and more than 92,000 form values.

This scale makes manual per-record correction impractical; the historical browser behavior needs to be modeled consistently.

## Common Failure Modes

### Running the scripts directly in Node.js

Modern V8 behavior differs from legacy JScript and IE document modes.

### Treating every page as IE11

Each screen's effective document mode must be resolved independently.

### Assuming `getElementById` has modern semantics

IE7 mode can also match a `name` attribute.

### Treating all whitespace as modern `\s`

Older JScript modes recognize a different whitespace set.

### Parsing all dates with modern `Date`

Legacy date parsing and two-digit-year behavior differ.

### Preserving LF in every textarea

Older MSHTML modes can expose CRLF.

### Assuming modern JSON serialization

Legacy pages can rely on compatibility implementations such as `json2.js`.

### URL-encoding the form values

The required result contains DOM values before HTTP encoding.

## Reconstruction Pipeline

A high-level reconstruction can be viewed as:

```text
journal entry
       ↓
select client screen
       ↓
determine document mode
       ↓
load keyed control state
       ↓
apply historical DOM rules
       ↓
execute equivalent script semantics
       ↓
recover named form values
       ↓
write postback.json
```

## Goal

IE Mode Postback reconstructs the application-visible state produced by a retired browser runtime without requiring that runtime to remain available.

The central principle is:

> Reproduce the semantics of the historical client, not the behavior of a modern JavaScript engine.
